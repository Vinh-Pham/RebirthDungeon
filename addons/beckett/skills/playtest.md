# Playtest suites - record, save, and rerun input runs as regression tests

> Turn a one-off agent playtest into a durable asset: record an input run, attach asserts and per-frame invariants, save it as `res://tests/playtests/<name>.json`, rerun it on demand or in CI, and repeat it n times to find out whether it is flaky. Deterministic (frame-exact) replay. Read `input` / `input-devices` for the event shapes and `gdunit4` for pure-GDScript unit tests (a different tool: `test_run`). The `playtest` tool is Full-only.

## Version note
- Server runs **4.6.2**; the frame-exact replay window and the `playtest` tool are Beckett **1.8+**. The 4.2+ engine floor holds: replay uses `Input.parse_input_event` and `flush_buffered_events`, `Expression`, `get_tree().paused`, the SceneTree frame signals and `Engine.max_physics_steps_per_frame`, all 4.0+.
- Events recorded on 1.8+ carry a frame stamp `f` (physics-frame delta). Older or hand-authored events without `f` still replay, but back-to-back (non-deterministic). Confirm with `get_godot_version`.
- **1.16** adds `op=repeat` (pass^k, flaky steps), `op=mutate`, `op=run_all` with `since` / `compare`, `op=export_gd` (a suite as ONE plain GDScript test that runs with no editor and no Beckett, for CI), the `blocked` verdict, per-frame `invariants`, the `inject` and `state` steps, the `no_overlap` assert (Full), `play_scene quiet=true` (every edition) and `get_remote_tree state=true` (a See tool, so Lite has it). Suites saved before 1.16 load and run unchanged. A suite that uses `invariants`, `inject`, `state` or `no_overlap` is saved as `schema_version` 2 (every other suite stays 1), so a Beckett older than 1.16 refuses it with "upgrade Beckett" instead of running it with the rules silently absent. The batch ops need the game running and connected, like `op=run`.

## The loop
1. `play_scene scene=res://your_scene.tscn` then `wait_until condition=game_connected` (the game must be running before you record or run - a handler cannot launch it and wait in one call). On 4.5+ a script error is logged to `game_logs` and the game keeps running; a game paused in the editor's debugger (4.4, a breakpoint, your own F5) answers every runtime call at once, saying so and what to do.
2. `record_input action=start`, drive the game (`simulate_input`, `click_control`, `type_text`, or a human at the keyboard), `record_input action=stop` - you get an `events` array, each event stamped with `t` (ms) and `f` (physics frame). For UI flows, read the screen between steps with `ui_snapshot` (one call: every visible control + state + `occluded_by`/`clipped` honesty flags) instead of screenshots; `click_control` auto-waits for clickability and refuses disabled/occluded clicks with the reason (1.10+).
3. `playtest op=save name=<name> scene=res://your_scene.tscn events=<those events> asserts=[...] invariants=[...]` writes the suite file.
4. Re-run any time: replay from a FRESH play session so the initial state matches the recording, then `playtest op=run name=<name>`. It replays deterministically and checks the asserts, returning `{verdict, ok, passed, failed, blocked, asserts:[...]}`.
5. Before you trust it as a regression test, `playtest op=repeat name=<name>` (1.16): five runs from a restarted scene each, and a straight answer to "is this suite flaky".
6. And `playtest op=mutate name=<name>` (1.16): a straight answer to "would these asserts notice if the game were wrong". Later, `playtest op=run_all since=<ref>` runs only the suites a change reaches.

## Play without disturbing the person: `play_scene quiet=true` (1.16)
When a human works on the same machine, a game window that pops up, takes their keystrokes and makes noise is the worst kind of test run. `play_scene scene=... quiet=true` (every edition) launches the game muted and out of their way; `wait_until condition=game_connected` then says what the GAME applied (`quiet: muted, window at (5320, 0) off every screen, no focus, still drawing`), and `get_play_state` carries it as `quiet`.
- **Muted**: the master bus, kept muted (a game that restores its volume in `_ready` is muted again within half a second; `remuted` counts it).
- **Parked, not minimized**: the game moves its own window past the right edge of the desktop, flags it no-focus and hands the keyboard back to the window behind. A minimized window stops drawing, and `screenshot` and the playtest tools read the frames a parked game keeps drawing. The first moments of a launch are still on screen.
- **By run mode**: a separate window (a headless editor, or Game Embed Mode off): as above. The embedded Game view (the default since 4.4) would switch the editor to its Game tab or open a floating window, so quiet makes it see embedding as unavailable for that one play (an in-memory setting, put back in the same call) and the game plays in its own window; the reply says whether the editor view stayed put, and a game that still ends up embedded only gets the mute. A headless game: only the mute.
- A quiet screenshot is the game window's own size. `quiet=false` forces a normal play; the person's own F5 is never quiet.

## Semantic steps suites (1.10+) - the layout-shift-proof alternative
Instead of `events`, save `steps`: a `ui_do` flow of `{click|type|wait|assert|input|inject|state}` objects addressed by SELECTOR (text/name/class), so the suite keeps passing when the UI moves - a recorded-coordinate replay would silently miss. `playtest op=save name=<n> scene=<res://...> steps=[{"click":"Start"},{"assert":{"node":"StatusLabel","property":"text","equals":"Status: start"}}] asserts=[...]`. `op=run` executes the steps through the game-side ui_do window (each step auto-waits; asserts poll until true), freezes, then evaluates the `asserts` array as usual. Trade-offs, stated plainly: steps suites are NOT frame-exact and capture NO perf stats (record `events` for the perf loop), and the headless CI runner SKIPS them - in CI, `op=export_gd` turns one into a standalone test that does run them (see Standalone CI test). One suite is events OR steps, never both. Every step result carries a status (see Verdicts), and the end-state `asserts` are only evaluated if the whole flow completed: after a flow that stopped they are reported `skip` ("stopped at step N") rather than read as failures of a half-played game.

## Verdicts: pass, fail, skip, blocked (1.16)
Every assert, every steps-flow step and every invariant ends with one of four statuses, and so does the suite:
- `pass` - it was evaluated and held.
- `fail` - it was evaluated and was false: an assert that read the node and found the wrong value, an assert step that timed out while its condition stayed false, an invariant that broke.
- `blocked` - the run could not get to a judgement: the scene failed to load, the game was not connected or the connection dropped, the node the assert reads was missing, a `wait` timed out before the assert behind it could run, an `inject` the game refused. Nothing was judged, so fix the setup (the scene, a node path, the connection), not the game logic. Only an assert can fail: a `click` or `type` whose control never became usable (missing, hidden, disabled, occluded) could not be performed, so it is blocked. If a button that stays disabled should FAIL the suite, add an `assert` step on its state (`{"assert":{"node":"StartBtn","property":"disabled","equals":false}}`) before the click.
- `skip` - not applicable here: a screenshot assert headless, a baseline saved on its first run, an end-state assert after a flow that stopped.

The suite verdict is `fail` if anything failed, else `blocked` if anything was blocked, else `pass`. `result.verdict` says which, `result.blocked` counts them beside `passed` / `failed` / `skipped`, and `ok` is true only for `pass`. A report carries the same verdict and `totals.blocked`; the blocked items sit in `failures` with their own `status`, so a reader that only knows pass/fail still finds the reason. A malformed assert (an unknown perf metric, an expression that does not parse) still FAILS loudly; an expression that parsed but could not be evaluated (a node it names is missing) is blocked.

## Assert types (the `asserts` array)
- `{"type":"node_state","target":"Player","property":"health","equals":3}` - a node property equals a value (numeric-tolerant: `3` matches `3.0`).
- `{"type":"expr","condition":"get_node('Player').position.y < 500"}` - a GDScript boolean evaluated against the scene root (same scope as `time_control op=step_until`). When it is false the detail also names the values it read (`...; read: get_node('Player').position.y = 512.3`), so a failure shows the number.
- `{"type":"screen_text","text":"You Win"}` - some visible node's `text` contains the string.
- `{"type":"screenshot","baseline":"res://tests/baselines/win.png","min_peak_snr":30}` - compares the live frame to a baseline PNG with `Image.compute_image_metrics` **peak_snr** (dB, higher = more alike). First run SAVES the baseline and skips; later runs compare. Reference points measured on 4.6.2/4.7: identical = 1e10, one changed pixel in 64x64 = 41.5, half the frame changed = 9.8, fully different = 6.8 - so the 30 dB default sits above AA/dither noise and below any real regression. Resolution is normalized to the baseline first (a window resize is not a regression). On failure it writes `<baseline>.actual.png` and returns both paths + the numbers, so you can look at them. Needs an RHI: SKIPPED (never failed) under the headless runner. The baseline is a path the run WRITES (first run and the `.actual.png`), and a suite file can come from a cloned repo, so it must be `res://` or `user://` with no `..` or control characters (1.16+): otherwise the assert is SKIPPED with the reason and nothing is written, headless runner included. `tolerance` from before 1.12 is no longer used and the result says so.
- `{"type":"perf","metric":"frame_ms_p95","max":20}` (Beckett 1.9+) - bound a measured perf metric from the replay window; `max` and/or `min`. Metrics: `frames`, `frame_ms_min/avg/p95/max` (the wall time from one frame to the next, ms, timed by the game itself since 1.17), `fps_min/avg` (the same clock), `memory_static_end`, `memory_delta`, `orphan_delta`, `draw_calls_end`. All measured, never estimates. A vsync'd 60 Hz game sits near 16.7 ms on every frame, so `frame_ms_p95 max=20` leaves it headroom where 16.7 would fail frames that met the refresh.
- `{"type":"no_overlap","paths":["Player"],"min_depth":0.1}` (1.16, Full) - no physics bodies penetrate each other, judged by the physics engine (see Clipping below). Every field is optional: with none, every body in the game is checked.

Asserts are evaluated AFTER the replay settles. `op=run` leaves the game FROZEN so reads are stable - call `time_control op=unfreeze` to resume. Each result keeps its place in the suite as `i` (`asserts[i]`).

## Invariants: rules that hold on every frame (1.16)
An assert looks once, at the end. A rule that was broken for three frames in the middle and mended itself passes every end-state assert; an invariant catches it. `playtest op=save ... invariants=[{"name":"hp_never_negative","expr":"get_node('Player').health >= 0"}]`:
- `expr` is a pure GDScript boolean, evaluated against the scene root exactly like an `expr` assert, on **every physics frame** of the replay window (and of a steps flow). It runs 60 times a second, so it must only read.
- It is judged at the START of each frame, so frame N sees the state frame N-1 left. `frame` is the replay's own physics-frame number, the same numbering as an event's `f`: "violated at frame 112" means the recorded event stamped `f=112` is the one to look at.
- The first violation of each rule is reported with its `frame`, the `expr`, and **the values it read** (the operands of its comparisons, evaluated on their own: `{"get_node('Player').health": -3}`; an operand that calls a game method is not run again, so it has no entry), plus how many frames broke it. A violated invariant FAILS the run.
- Each rule shows up in `result.asserts` as `{type:"invariant", name, status, checked, violations, first_violation}`, ahead of the end-state asserts. A rule that was never once evaluated (every frame errored, so no node to read) is `blocked`, not `pass`. An error on some frames only is counted in `errors` and is not a violation.
- At most **16** rules (each costs one expression evaluation per frame; a rule that errors every frame costs ~100x one that evaluates). Names must be unique. `op=save` refuses a rule that does not parse, naming it.
- Use `get_node_or_null('Boss')` (and guard with `... == null or ...`) for a node that may not exist yet: `get_node` on a missing path logs an engine error on every frame.
- They need the deterministic replay window or a steps suite. A non-deterministic replay (events with no `f`, or `deterministic=false`) has no per-frame window, so its rules are `skip` with the reason.

## The inject step: set up the state, then look (1.16)
A steps suite can patch state into the live game and verify from there, instead of playing for minutes to reach it: `{"inject":{"set":[{"node":"Player","property":"health","value":0}],"call":[{"node":"Spawner","method":"spawn","args":[3]}],"frames":2}}` (the flat spelling `{"kind":"inject","set":[...],"call":[...],"frames":2}` is the same step).
- It goes through the same game-side machinery as `runtime_set_property` / `runtime_call`: values are coerced to the property's type (`[x,y]` for a Vector2), writes are read back, call arguments are coerced to the declared types.
- Every target node must exist before ANYTHING is applied (a menu or a spawned enemy may not be there yet, and a call is not idempotent): the step waits for them under its timeout, then applies all `set` entries, then all `call` entries, once.
- Then it holds for `frames` frames (default 1, at most 600; both process and physics frames must have elapsed) so the next step reads the state AFTER the game ran on what you injected. Typical flow: `inject` health 0, `frames` 2, `assert` the game-over panel is visible.
- The step result lists what changed (`applied`: `set Player.health: 3 -> 0`). A write or call the game refuses, or a target that never appears, ends the step `blocked`; a malformed inject is refused at `op=save`.
- It is a `ui_do` step kind, so it also works in a plain `ui_do steps=[...]` call.

## Repeat: pass^k, flaky steps, first divergence (1.16)
One passing run says little about a game with any randomness in it: a model that scores 51.7% on one attempt can be at 39.4% when it has to pass five times out of five (OpenGameEval, arXiv 2610.02563). `playtest op=repeat name=<suite> n=5` (1 to 50) runs the saved suite n times back to back and reports the mean next to pass^k. The scene is RESTARTED before every run (including the first), so each starts from the same clean scene and the second run does not measure what the first left behind; a key the previous run never released is let go too. It does not need a fresh `play_scene`.
- `runs`, `passes`, `fails`, `blocked`, `pass_rate` (the mean), **`pass_all`** (pass^k: true only when ALL n requested runs passed), `verdict`, `outcomes` (the verdict of each run).
- `steps`: every assert / step / invariant with its outcome counts (`{pass:4, fail:1}`) and one example detail of each non-passing outcome.
- `flaky_steps`: steps whose pass/fail outcome FLIPPED between runs, most flips first (`{step:"asserts[2]", flips:4, outcomes, examples}`). `flaky_blocked` ranks the flips to or from `blocked` separately: a node that is sometimes missing is a different finding from a value that is sometimes wrong. A `skip` flips nothing.
- `first_divergence`: the first STEP (in step order) whose observed result differs from run 1, with both details (`was` / `now`), or `null` when every run looked the same. It compares what the game said, so it catches an assert that fails with a different value on each run, which no count shows. A perf unit compares by status only (its numbers differ every run).
- One call blocks the editor for at most about 45 s. A longer batch stops early: `truncated:true`, `runs` below `requested`, `pass_all` false (pass^n was not shown), and a note. Shorten the suite or call again for another batch; each call is its own batch.
- A restart resets the SCENE and the resources it names (re-read from disk, in place), not the process: whatever lives outside them (autoloads, saved files, engine singletons, a script's own variables) carries over, and a suite that depends on it reads as flaky here. The batch restarts the scene once more when it ends, so a following `op=run` starts clean (`run_all`: on the scene it found). A scene built in code (no scene file) cannot be restarted: that is an error on the first run, with the way out (`stop_scene`, `play_scene`, and `op=run` for each attempt).
- `save_baseline` and `report` are ignored (a batch neither stamps a baseline nor writes a report). A run that errors is recorded `blocked` with its reason in `run_errors`; if the game connection is lost the batch stops (`aborted`).
- A restart waits up to 15 s for the scene to come back: a heavy 3D scene can block the game's main thread for several seconds while it loads, and a poll that times out meanwhile is waited out, not fatal. A run that times out is recorded `blocked`; two in a row stop the batch (the game stopped answering: ask `get_play_state` for `debugger_break` first, and an embedded game may be Suspended). A game paused in the editor's debugger stops the batch at once, with the whole answer and its next step.
- Reading it: all `pass` with `pass_all` true = the suite is stable. `flaky_steps` empty but `first_divergence` set = the suite fails the same way every time yet the game does something different each run (an unseeded random, a timing race). `flaky_blocked` only = fix the scene or the node path before suspecting the game.

## Mutate: would these asserts notice a fault? (1.16)
A suite that passes says the game did what it asserts. It does not say the asserts would have caught anything. `playtest op=mutate name=<suite>` checks that: it runs the suite clean once, then reruns it with ONE fault put into the game at the start of each fresh replay, and counts the faults the suite catches. (GameLogicBench, arXiv 2609.21562, validates its evaluators the same way: an implementation with one capability removed must fail, and without that check wrong solutions passed.)
- **The clean run comes first, and a suite that does not pass on its own is refused** (`verdict fail` or `blocked`, with the failing assert): on a red suite every fault would look caught, which proves nothing.
- **The faults come from what the suite NAMES**: the nodes and properties its asserts, invariants and steps read (a `node_state` target, `get_node('X').prop` inside an expression, a steps `assert` or `wait`, the nodes an `inject` names). A number is set to 0 and negated (a property already at 0 is set to 1 instead, since both would change nothing), a bool is flipped, a node's `process_mode` is set to disabled (its `_process`, `_physics_process` and `_input` stop), and ONE signal connection the suite's scene declares is cut (an unbound one, preferably on a node the suite names). A string, vector or object property has no fault and is listed under `skipped` with the reason; a name that is not there says so too. One node named two ways in the suite (`Game` and `/root/Game`) is one target: its faults are tried once and list the asserts of both spellings.
- **How a fault goes in**: through the same game-side write path as the `inject` step (value coercion, read back), on the freshly restarted scene while it is still frozen, so it lands before the first frame of the replay. The scene is restarted again before the next fault. A property changed outside the scene (an autoload: a restart does not reset it) is written back afterwards, and the game ends on a fresh, frozen scene on the suite's own scene.
- **Result**: `total` (faults judged), `killed` (the suite failed or went blocked), `survived` (it still passed), `score` (killed / total; null when nothing was judged), `survivors` [{target, operator, change, reads, hint}], `caught` [{target, operator, change, by}] (`by`: the failing assert that READS the faulted value, else the first one that failed), `skipped` [{target, why}], `planned`, `not_run`, `next_from`.
- **A survivor is an assert that cannot fail for that fault.** `hint` says what nobody noticed (`no assertion notices Player.health = 0`) and `reads` which asserts read it. Either the run does not depend on that value (the game rewrites it, or the assert reads something else) or the assert is looser than the thing it guards: assert on the value, tighten the threshold, or drop the assert that proves nothing. Not every survivor is a bug: a fault the game legitimately absorbs (a heal that restores health) survives by design, so read `reads` before you act.
- **Bounds**: `max` (1-50, default 10) is the faults tried per call, and one call stops at the ~45 s the editor may spend (`truncated`). When `next_from` is present, call again with `from=<next_from>` for the rest. The faults are listed breadth first (every target's first fault, then every target's second), so a small `max` samples the whole suite instead of exhausting one property. A run that errors before judging anything (the game stopped answering) is `inconclusive` under `skipped`, never a kill; a lost connection stops the batch (`aborted`) with `next_from` pointing at the fault to retry.
- **Mutate a stable suite.** A kill is "the suite no longer passed", so a suite that flips between runs (a physics assert a frame off, an unseeded random, a window that lost focus and let go of a held key) makes some faults look caught for the wrong reason. `playtest op=repeat` first; `by` helps you see it (a caught fault credited to an assert that does not read the faulted value is the sign).
- Unit of work: one restart plus one replay per fault, so a suite that takes 3 s costs about 3.5 s a fault. Mutate a short suite, or lower `max`.

## Run every suite, or only what a change reaches (1.16)
`playtest op=run_all` runs every saved suite in name order, each from a restart of ITS OWN scene (a suite that saved no scene runs on the current one), so one `play_scene` is enough, not one per suite. It returns `suites` [{name, verdict, passed, failed, blocked, skipped, mode, scene, ms, problem}] (`problem`: the first assert that did not pass), the counts and the overall `verdict` (`ok` is true only when every suite ran and passed). A suite whose scene file is gone is `blocked` with that reason and the batch goes on. Steps suites run too (the headless runner skips them). One call stops at the ~45 s the editor may spend (`truncated`, `next_from`): call again with `from`.

`since=<git ref>` runs only the suites a change can reach (Unity's CLI ships the same pair: `unity test --affected --since <ref>` and `--affected-compare`). It asks git what differs from the ref (`git diff --name-only <ref>` plus the untracked files, relative to the project), then keeps a suite when a changed file is:
- the suite's own file, or a screenshot baseline its asserts compare with;
- its scene, or anything the scene loads: resources through the engine's dependency list, and scripts through the `res://` literals in `preload` / `load` / `extends "..."` and through `class_name` use (a script has no dependency list of its own, so its text is read). A literal that names a folder or the front of a built name (`"res://data/jobs/"`, `"res://levels/lv_%d.tscn"`) counts as everything under it: a loop over a folder is how a data-driven game loads its content;
- and a suite with no saved scene is selected by any change that matters (what it loads is unknowable).

A change selection cannot place selects EVERY suite, and `selection.why` says what: `project.godot`; an autoload, a resource a project setting names (the audio bus layout, a default environment, the project theme, a cursor) or anything those load or sits under a folder they spell out (the Beckett runtime is an autoload; so is a `Content` script that walks `res://data/`); a data file no resource references (JSON, CSV, text: a script may read it by path, and a dependency list cannot rule that out). Docs, CI config, scripts for the tooling and `.uid` files select nothing. A scene, script or image that no suite loads reaches no suite (it is listed under `selection.unreached`). `selection` is {since, mode: `impact` | `all`, why, changed, ignored, selected, skipped, reasons{suite: why}, unreached}. When nothing selected needs running the call says so and runs nothing (no game needed, not an error).

`compare=true` (needs `since`) runs EVERYTHING, then reports `compare` {would_run, would_skip, checked, skipped_failed, skipped_blocked, false_negatives}: the suites selection would have skipped that failed anyway. That is the false-negative count, and it is the number that says how far to trust `since`. A skipped suite that fails has either been reached by the change in a way the dependency list cannot see, or was already red before it (rerun on the ref to tell); a skipped suite that is blocked judged nothing and is listed apart.
- **What selection cannot see**: a path a script gets without writing its front down: read from a file or a setting (`load(config["level"])`), or put together from pieces none of which starts with `res://`. The file it loads is in no suite's closure, so changing it selects nothing. Run `compare=true` now and then (every release, or after you add a loader like that): `false_negatives` above 0 with a green selection is exactly this.
- `since` needs `git` on PATH and the project inside a repository; a ref that starts with `-` or holds whitespace, quotes, backslashes, `$`, backticks or control characters is refused before git runs, so git gets one plain argument. The usual refs work: `HEAD` (uncommitted changes only), `HEAD~3`, a branch, a tag, a commit hash, `main..HEAD`.
- The headless CI runner always plays every suite; `since` is the in-editor path, for the loop where you change something and want to know what it broke.

## Clipping: `no_overlap`, the physics engine as the oracle (1.16, Full)
A vision model is wrong both ways on geometry clipping: it flags objects that merely touch and misses a collider buried in a wall (arXiv 2607.25921). The physics engine knows exactly, so ask it: `{"type":"no_overlap"}` in `asserts`, 2D and 3D. At the settled, frozen end of the run the game asks its physics space what each enabled shape overlaps and measures each candidate pair on its own; a pair counts when its deepest contact is more than `min_depth`.
- Fields (all optional): `paths` (node paths; a node that is not a body stands for the bodies below it), `group`, `min_depth`, `max_pairs` (1-200, default 20: the scan stops there), `max_bodies` (1-2000, default 500). With no `paths` or `group` every physics body is checked, each against every other body in its space, named or not.
- `min_depth` defaults to 0.5 in 2D (pixels) and 0.05 in 3D (meters); a number you give applies to both. A body at rest sinks 0.3 px (2D) or 0.01-0.02 m (3D) as the solver keeps contacts stable, so a smaller bound flags everything standing on the floor; touching shapes (depth 0) are never a pair.
- Never counted: Areas, disabled shapes, 2D one-way shapes, a body and its own ancestors or descendants, bodies whose layers and masks never interact, collision exceptions (joints add them), and two STATIC bodies unless one is named (level geometry overlaps by design). A pass says how many bodies it checked and what it left out.
- A fail lists `pairs`: `{a, b, depth, normal, at, space}`; `normal` points from `a` toward `b` (move `a` by `-normal*depth` to separate them), `at` is where they meet. Detail: `no_overlap: 2 pair(s) penetrate more than 0.5 (2D) / 0.05 (3D): Flat/Block into Flat/Pawn, 5.0 deep; Hero into Wall, 0.8 deep`.
- **blocked**, never a pass: a path or group that names nothing, no body found, or a scan that did not finish (more bodies than `max_bodies`, or its ~1.5 s budget ran out). Raise `max_bodies`, or scope with `paths`.
- It finds a CharacterBody, kinematic or static body that ends up inside another (a spawn point in a wall, tunnelling, a platform through a wall). A RigidBody that starts inside a wall is pushed out by the solver within a few frames: give it `settle_frames`. The headless runner runs it too; `op=export_gd` lists it as `not_run`. The runtime command behind it is `physics_overlap`; there is no tool of its own.

## Perf measurement + baseline (1.9+)
- Every deterministic `op=run` also MEASURES the replay window and returns the flat stats above as `result.perf` - no extra flag needed.
- `playtest op=run name=<name> save_baseline=true` stamps this run's stats into the suite file. Every later run returns `result.perf_diff` = per-metric `{baseline, current, delta, delta_pct}`.
- The optimize loop: run with `save_baseline=true` once -> change code -> fresh `play_scene` -> `op=run` -> read `perf_diff` ("frame_ms_p95 +2.1 ms = you made it slower"). Add a `{"type":"perf",...}` assert to make the suite FAIL on a perf regression in CI.
- A baseline also stores a fingerprint of where it was measured: OS, CPU, GPU adapter + vendor, display server, renderer + driver, viewport size, engine, debug/release, and a hash of the recorded run. Every later run returns `result.perf_baseline_comparable` (`true`, `false`, or `"unknown"` for a baseline saved before 1.16 when the game also runs a runtime older than 1.17; one saved before 1.17 reads `false`, `perf_clock 1 -> 2`) and `perf_baseline_mismatch` = `{field: [baseline, now]}`. When it is `false`, `perf_diff` is still returned but compares unlike runs - read it as "different machine", not "regression", and re-capture with `save_baseline=true` on this setup. Absolute `perf` asserts never depend on the baseline.
- Frame/fps/draw metrics are only honest with a WINDOWED game: for a headless play session (or the headless runner) they are SKIPPED with a note; `memory_delta` / `orphan_delta` stay valid everywhere.
- **A batch measures a cold scene.** `op=repeat`, `op=mutate` and `op=run_all` restart the scene before every run, so the replay window starts right after the load: a heavy scene that keeps building after its `_ready` puts those frames into `frame_ms_*` (a 3D village measured p95 6,243 ms after a restart and 76 ms on a scene that had been running). A perf bound that is broken in a batch is therefore reported `blocked` with that reason, not `fail`, and one that holds still passes (cold is the worse case). Judge perf with `op=run` on a scene that has been running.

## Determinism (why replay reproduces exactly)
- Replay opens a game-side window that unpauses, puts each event in between frames (the one stamped `f` right after frame `f`), then re-pauses. The game is UNPAUSED when an event goes in, so both `_input()` callbacks AND polled `Input.*` (e.g. `Input.get_vector`, `is_action_pressed`) see it - a naive freeze-then-inject would miss `_input` on pausable nodes.
- Same recording + same starting scene = same frames = same result, every run. This is the regression guarantee. It holds ONLY if the run starts from the same initial state: record right after a fresh `play_scene`, and rerun from a fresh `play_scene` too (`op=repeat` restarts the scene itself).
- An event stamped `f` acts from physics frame `f+1` (a key pressed at f=3 and held acts from frame 4) for `_input`, polled state and `is_action_just_pressed` alike. The editor's replay, the headless runner and the exported test all put it in between frame `f` and `f+1`, outside physics, and run one physics frame per engine frame while they replay (1.17), so they run the same physics frames every time, even on an engine that falls behind. One idle frame differs: `op=run` judges its asserts after its settle frame (`_process`, idle Timers and Tweens move on one real-time frame), the runner and the exported test before it, so a value only `_process` changes can read one frame apart.

## Headless CI (the runner)
Run every suite outside the editor, exit non-zero on any failure:
```
godot --headless --path <project> res://addons/beckett/runtime/playtest_runner.tscn
```
It scans `res://tests/playtests/*.json`, plays each scene, replays deterministically, checks asserts and invariants, prints `[playtest] ok/FAIL/BLOCKED <name>` plus a measured perf line, and exits **1** if any suite failed, else **2** if any was BLOCKED (the scene would not load, a node an assert reads was missing, the scene freed itself or the game quit mid-run, or it changed scenes, which replaces the runner: use `export_gd` for that game; nothing was verified, which is not a pass), else 0. `node_state` / `expr` / `screen_text` work headless, and so do `perf` asserts on `memory_*` / `orphan_delta`; `screenshot` asserts and rendering-cost `perf` metrics (`frame_ms_*` / `fps_*` / `draw_calls_*`) skip (no RHI - a render-less loop's frame numbers would prove nothing). The runner does not repeat suites (use `op=repeat` in the editor), does not mutate them (`op=mutate`), and always plays every suite: selecting by change is the editor's `op=run_all since=<ref>`. A key a suite leaves down is let go before the next suite starts, and the runner reads `node_state` as a plain property (`health`, not a sub-property path like `position:x`: use an `expr` assert for that, or the exported test below, which reads both). Wire this into your own CI to keep the playtests verifying forever.

## Game-owned state: `_beckett_state()` (1.16)
A property read cannot tell which of a node's fields matter, and a screenshot cannot show a number the UI never draws. So the game can say what its state is: put a node in the group `beckett_state` and give its script `func _beckett_state() -> Dictionary` that returns plain data (numbers, strings, bools, arrays and dictionaries of them; a Vector2 or a Color is fine, it is read as text). The other spelling in use, the group `mcp_state` with `_mcp_state()` (leftos/godot-mcp and wgt19861219/godot-mcp-enhanced), works unchanged; a node that has both is read through `_beckett_state`.
```
extends Node2D
func _ready() -> void:
	add_to_group("beckett_state")
func _beckett_state() -> Dictionary:
	return {"hp": health, "inventory": items, "stats": {"speed": speed}, "phase": "boss"}
```
- **Read it** with `get_remote_tree state=true` (a See tool, Lite has it; `depth=0` reads just the state). It returns `state: {<node path>: {...}}` for every such node of the WHOLE game, autoloads included, keyed by its path (relative to the scene root, or `/root/...`). The reply is capped (40 nodes, 6,000 characters a node, 12,000 in all, 64 entries a list, depth 6, 120 characters a string) and says so: `state_truncated` and `state_truncated_nodes`. A node that is in the group but cannot answer (no method, or it did not return a Dictionary) is listed in `state_errors` with why, and with no such node at all `state` is `{}` and `state_hint` says how to add one.
- **Assert on it** (Full) with a steps suite's `state` step: `{"state":{"node":"Player","path":"inventory.0","op":"eq","value":"sword"}}` (flat spelling `{"kind":"state","node":...,"path":...,"op":...,"value":...}`; a suite that uses it is schema 2). The step only needs the method on the node you name; the group is what `get_remote_tree state=true` uses to find it. `path` is dotted into the dictionary: keys, array indexes (`inventory.0`, and `-1` is the last), components of a Vector or Color (`pos.x`). `op` is `eq` (default), `ne`, `lt`, `le`, `gt`, `ge`, `contains` (a string, an array, or a dictionary key) or `exists` (`"value":false` asks for a key that is NOT there). The expected `value` is coerced to the type the state holds, so `[1, 2]` matches a Vector2, `"true"` a bool and `3` matches `3.0`.
- It polls like an `assert` step, until it holds or the step times out. **fail**: the state was read and stayed wrong (or cannot be compared that way, e.g. `gt` on a string against a number). **blocked**: nothing could be judged, because the node never appeared or has no `_beckett_state()` (or it did not return a dictionary). A malformed step is refused at `op=save`.
- An events suite has no steps: read the same thing with an `expr` assert, `get_node('Player')._beckett_state().hp > 0`.
- `op=mutate` counts the node a state step reads (it can disable it) but not the keys of its dictionary: they are not properties it could fault.

## Standalone CI test: `op=export_gd` (1.16)
The headless runner above needs the addon, skips steps suites, and plays every suite or none. `playtest op=export_gd name=<suite>` writes ONE suite as a plain GDScript test, `res://tests/beckett/<suite>_test.gd` by default (`path=` for another `.gd` file inside the project), that needs neither the editor nor Beckett. The addon can be switched off or not installed at all: the file never names it.
```
godot --headless --path <project> --script res://tests/beckett/<suite>_test.gd
```
- It loads the suite's scene and replays the events frame by frame with the timing `op=run` uses (the rules judged first on each physics frame, the asserts once the settle frames have passed), or runs the steps flow. It prints one line per judgement (`pass`, `fail`, `blocked` or `skip`, the name and the detail: `fail    asserts[0] node_state: Player.position:x = 7.0 (expected 10.0)`), then a summary and, last, `BECKETT_RESULT {suite, verdict, passed, failed, blocked, skipped}`. Exit **0** pass, **1** fail, **2** blocked (nothing failed, but the scene or a node was missing, or the game quit mid-run: nothing was verified, which is not a pass). Node paths are read on the scene the game is in at that moment, as the editor reads them, so a game that changes scene mid-run is judged on the new one.
- It runs `node_state`, `screen_text` and `expr` asserts, the invariants, and in a steps suite `click`, `type`, `wait`, `assert`, `input`, `inject` and `state` steps. `click` and `type` push real input into the viewport but do not check that the control is uncovered or on screen, and do not scroll it into view (the editor's do). It does NOT run `screenshot` asserts (they need a rendered frame), `perf` asserts (the editor's replay window measures them, and a render-less CI loop has no frame cost to bound), an unknown assert type or an unknown step kind. Those come back in the reply as `not_run` and sit as comments in the file's header, so nothing is dropped silently; the test prints an assert it cannot run as `skip`, and an unknown step fails the flow there, as it does in the editor.
- An event stamped `f` acts from physics frame `f+1`, as in the editor's replay (see Determinism). A run takes about as long as the recording; add `--fixed-fps 60` (the project's physics rate) and the engine runs it as fast as the machine allows instead (a 30 s recording took 0.4 s, with the same physics frames: logic keyed to the wall clock or to `_process`'s delta sees another clock). The test gives up with `blocked` if the game keeps the tree paused, or the machine is far slower than real time.
- Everything the file takes from the suite is escaped, so a node path, an expression or a name cannot turn into code. The file does execute the suite's own `expr` strings, exactly as `op=run` does: read a suite you did not write before you run it, as you would any test.
- Safe to rerun: an existing file is replaced only when an earlier export wrote it (its first line says so); a script you wrote is never overwritten, and a `path` outside the project, with `..`, or not ending in `.gd` is refused. The file is a snapshot: export again after the suite changes, and commit it with the project. Each file carries the whole runner (about 78 KB), so a handful of suites is fine, and for a hundred the shared headless runner above is the smaller choice. It is a script in your project like any test, so keep `res://tests/*` out of your export presets (Beckett's export filter only strips Beckett's own files).

## Common traps
- **A survivor is a question, not a verdict.** A fault the game legitimately absorbs (it heals the player, recomputes a score) survives by design, and a loose assert (`x > 40` when x ends near 60) survives a nudge of 1. Read `reads` and the `change` before you rewrite an assert, and prefer asserting on the value that matters over loosening the check.
- **`since` is a bet on a dependency graph.** It is right for everything that is referenced (scenes, resources, scripts, `preload`, `class_name`, a folder or name front a script spells out) and blind to a path a script gets without writing its front down. When in doubt, `compare=true`; when it reports a false negative, either load the file by a literal somewhere a scene can see, or accept running everything for that area.
- **mutate and run_all restart the SCENE, not the process.** Whatever lives outside it (an autoload, files on disk) carries from one run to the next, as with `op=repeat`; mutate writes back the autoload properties it faulted, but not what the GAME changed in one. A scene built in code (no scene file) cannot be restarted: an error that says how to continue. And a script you edited after `play_scene` is NOT reloaded by a restart (the game keeps the version it loaded): `play_scene` again after editing code, before `run_all since=...` or `op=mutate`.
- **`run_all` leaves the game on the last suite's scene, frozen** (the same contract as `op=run`). `time_control op=unfreeze` to carry on playing.
- **Keep other windows out of the way while a batch runs.** When the game window loses focus, Godot lets go of every key it holds. A click elsewhere, or another program opening a window, in the middle of a replay cuts a held key short: the walk ends early, the position assert fails, and under `op=mutate` a fault that should survive reads as killed (or the clean run fails and the suite is refused). A failure that goes away on the next run is this, and `op=repeat` shows it as a flaky step. `play_scene quiet=true` (above) avoids it: a window that never had focus has none to lose.
- **Record with KEY / mouse / joy / touch events, not `action`.** The recorder serializes real `InputEvent`s; synthetic `InputEventAction` (`simulate_input type=action`) is NOT captured. Drive `ui_right` by injecting `type=key keycode=Right` (the Input Map maps it to the action), which both records AND drives the action system.
- **The game must be connected first.** `playtest op=run` assumes a live, connected play session (`play_scene` then `wait_until game_connected`). It will not start the game for you.
- **Determinism needs a matching start state.** Replaying onto a game that is mid-level (already moved) will not reproduce the recording. Always rerun from a fresh `play_scene`; `op=repeat` restarts the scene before every run, which resets the scene and nothing outside it.
- **blocked is not failed.** A blocked suite says the run could not judge, not that the game is wrong. Read the reason on the blocked item (a missing node, a lost connection, a timed-out wait, a game paused in the editor's debugger) and fix the suite or the setup. CI should treat blocked as red too: it verified nothing.
- **An invariant is a rule, not a probe.** It runs every frame: no side effects, no `get_node` on a path that may not exist yet (`get_node_or_null`), and at most 16.
- **A state step trusts what the game says.** It reads `_beckett_state()`, not the screen and not a property: if that method returns a cached or derived value that can go stale, the step passes on the stale value. Keep it a plain read of live fields, with no side effects (it is called on every poll).
- **An exported test is a snapshot.** It holds the suite's data as it was when `op=export_gd` ran. Edit the suite, export again. It is also not the editor's run: no screenshot or perf judgement, and a click does not check what covers the control (see Standalone CI test).
- **Raw hardware polling is a blind spot.** Replayed events drive the action system and `_input`, not `Input.get_joy_axis(device, ...)` raw reads - the same caveat as all synthetic input (see `input-devices`).
- **`screenshot` asserts need a window.** They pass/fail in an in-editor run (the played game has an RHI) but SKIP under `--headless` (the runner asks the DisplayServer, so a windowed runner DOES compare) - keep node-state / expr asserts for the headless CI path, screenshots for local visual checks.
- **An in-editor run is normally EMBEDDED.** Since 4.4 the editor plays the game inside its Game workspace by default (and "Make Game Workspace Floating" is still embedded). That still has an RHI, so screenshot asserts really do compare - but the frame is sized to the workspace panel, not to your project resolution. A baseline recorded at another size is compared after a resize to the baseline, and the result says so (`[current frame resized to the baseline's WxH]`): record and rerun a baseline from the same placement and panel size, or the resample noise eats the dB margin. `doctor` reports `game_view.mode` and `game_view.placement`. A `quiet=true` play is never embedded (it plays in its own window): its frames are the window's own size.
- **`op=run` leaves the game frozen.** That is intentional (stable asserts); call `time_control op=unfreeze` before you keep driving.
- **`playtest` is not `test_run`.** `test_run` runs pure-GDScript `test_*` methods (unit tests, ships in Lite); `playtest` replays input into the RUNNING game and checks live state (Full). Use both.
- **One gesture = ONE `simulate_input` call.** Split press / move / release across separate calls and the host's real mouse can interleave between them, corrupting drags and aim. Atomic event lists also record/replay clean.

Confirm class, property, and method names with `describe_class` (e.g. `class=Input`, `class=Expression`) and `get_godot_version` before relying on them.
