# Phase 5 combat implementation and verification

Implementation recorded 2026-09-10. **Phase 5 remains open for native acceptance.** The tracker retains the Android/iOS interaction and cross-platform replay gates; this document does not claim physical-device acceptance.

## Delivered behavior

New production runs enable the existing deterministic combat rules. `BattleHud` owns a stable Scene2D hierarchy over a separate world viewport: resources/reservations, five die-ID slots, kept markers, rerolls, score, locked skill/target, observed enemy HP, separate Roll/Reroll/Use/Pass controls, inspection, status details, six face probabilities, combo reference and bounded filtered event log. Compact mode uses inspection for detail and preserves primary controls. UI scale, reduced motion, sound and optional haptics are presentation-only preferences lasting until application exit.

`BattleView` supplies detached availability and session/revision identity. `DungeonInput` and `InputOwnership` give modal/UI/world routing, gesture ownership, stale/duplicate rejection, focus navigation and cancellation. Keys 1–5 toggle kept slots; Tab/Shift-Tab navigate, Enter/Space activate, Escape/Back dismisses the top surface before Menu. Post-roll Pass confirms its reserved costs; cancellation retains the hand. A queued UI request displays Saving before the synchronous controller save; subsequent actions remain blocked on failure until Retry save succeeds. Menu navigation preserves the active run. Only defeat permits ordinary retry; an exit marker or encounter victory is not expedition completion.

`CombatTracks` consumes ordered observed events once, bounds cosmetic movement/attack/damage/death/camera feedback and reconciles to the final observation. Skip and reduced motion cannot issue simulation commands. Audio uses an AssetManager-owned original cue generated by `tools/make_combat_sound.py`; optional haptics use the platform capability through the feedback interface. Physical haptic behavior is unverified.

## Checkpoint boundary

`game/projection/CombatRestore.kt` exports detached restore-only actor and encounter state. It includes dead-hero/outcome state, resources/reservations, statuses/sources/durations, shields, cooldowns, selected and locked definitions/ranks/targets/stat inputs/profile, five faces and kept slots, and reroll budget. Existing run exports retain RNG, initiative, map and command continuation. Restore validates identities, costs, catalog agreement, stats, limits and activation consistency before constructing the world; it does not tick durations, reroll or refill resources. HUD code reads observations, never the full hidden-entity restore export.

`data/save/codec/CombatCheckpointCodec.kt` explicitly encodes version-1 positional primitive JSON records inside the optional outer DTO `combat` string. Record arity/types, duplicate maps and long identifiers are checked; it does not serialize ECS classes reflectively. Existing movement-only payloads with no combat field remain readable as movement sessions. No automatic content-version migration is claimed. Save retry rewrites the same committed state, and accepted player/enemy actions checkpoint through the application controller.

`USE_ITEM` remains unavailable because inventory ownership and atomic consumption do not exist. Its conditional Phase 5 task is explicitly deferred to Phase 7: one restorative potion and one temporary-side-effect potion as pre-roll full actions. Profile persistence and expedition reward policy remain later phases.

## Reproduction and evidence

Normal desktop launch: `./gradlew :lwjgl3:run`. For a repeatable developer encounter, set `REBIRTH_COMBAT_ARENA=1` and optionally `REBIRTH_CHECKPOINT_DIR=/tmp/rebirth-phase5-arena`. The developer-only 8×5 arena places the hero next to an enemy and exposes **Dev new run**. Do not use this reset control as evidence for production run replacement policy.

Final verification on macOS arm64, Gradle 9.5.1 / daemon JVM 25:

```sh
./gradlew :core:check :lwjgl3:compileKotlin :android:checkDebugDuplicateClasses :android:assembleDebug --console=plain --info
```

Result: **BUILD SUCCESSFUL; 90 tests, zero failures/errors/skips**. See [build log excerpt](evidence/phase5/gradle-verification.log), generated `core/build/test-results/test/` and `core/build/reports/tests/test/index.html`. Tests in `game/combat/CombatCheckpointTest.kt` cover checkpoint continuation after each command, reservations/locked inputs, status/shield/defeat restoration, malformed state, save failure/retry and stale requests. `presentation/BattlePresentationTest.kt` covers ownership/repeats/cancellation, availability and event replay/skip invariance including lethal damage feedback.

Real desktop controls were exercised in a temporary jpackage app containing the project's desktop jar. Verified:

- All-kept rejection, two spent batch rerolls and [zero-reroll availability](evidence/phase5/desktop-zero-rerolls.png).
- Skill use and enemy responses leading to [victory](evidence/phase5/desktop-victory.png); repeated Pass leading to [defeat](evidence/phase5/desktop-defeat.png), followed by retry.
- Exact-cost post-roll Pass confirmation, Escape cancellation, menu return and keyboard focus.

These captures precede only the final zero-size render guard and minor skill-menu separator edit, which passed the final build above.

## Unmet native gates

Android duplicate-class validation and debug APK assembly pass. The APK was installed/started on the Medium_Phone emulator, but this is **not** acceptance of touch combat, two-pointer behavior, safe insets, focus/back, short landscapes or device haptics. Repeat the tracker interaction matrix on Android.

`./gradlew :ios:launchIPhoneSimulator` completed RoboVM AOT/link/sign during this implementation; Xcode 27's renamed Simulator helper still produces `Unable to find application named 'Simulator'`. Direct `simctl install`/`launch` on iPhone SE (3rd generation), iOS 18.2, revealed a separate blocker:

```text
java.lang.NoClassDefFoundError: java/lang/BootstrapMethodError
Jackson ExceptionUtil.isFatal → JacksonAnnotationIntrospector
→ ObjectMapper → JacksonContentRepository → RebirthDungeon.loadContent
```

The loading screen now catches the linkage failure and retains an actionable diagnostic ([simulator screenshot](evidence/phase5/ios-loading-error.png)); no gameplay was reached. Dependency pins were not changed and no platform shim was introduced. Resolve the Jackson/RoboVM runtime compatibility, rebuild the latest source through full AOT and repeat real iOS combat controls plus cross-platform checkpoint continuation. A launch PID, Kotlin compilation or AOT result alone does not close that gate.

Wide/compact behavior is desktop-verified only at the recorded sizes. Full overlapping-panel, multi-pointer, zero-size native resize, interruption, mobile accessibility and safe-area acceptance remain in the Phase 5 matrix. Until those checks pass, the phase overview and target-wide exits stay unchecked.
